## 0. 한눈에

1. **연구1**: 오류를 넣은 시나리오에서 자동화 수준(높음/낮음)만 바꿔, 통제감 상실이 생기는지와 어디서 생기는지 관찰했다.
2. **가이드라인**: 연구1에서 관찰된 통제감 상실을 해결하도록 도출했다.
3. **연구2**: 같은 시나리오에서 자동화 수준은 높음으로 고정하고 가이드라인 적용 여부만 바꿨다. 기존안은 연구1 그대로라 오류가 생기고, 개선안은 가이드라인대로라 오류가 생기지 않는다. 이 차이로 통제감 상실이 줄어드는지 측정한다.

| | 연구1 | 연구2 |
|---|---|---|
| 시나리오 | 택시 호출 (오류 2곳 포함) | 연구1과 같음 |
| 바꾼 것 | 자동화 수준 (높음/낮음) | 가이드라인 적용 (기존안/개선안) |
| 고정한 것 | 오류 있음 | 자동화 높음 |
| 오류 | 두 조건 모두 발생 | 기존안만 발생 |
| 본 것 | 통제감 상실이 생기는가, 어디서 생기는가 | 통제감 상실이 줄어드는가 |

## 1. 면담 피드백 요약 (Figma 코멘트)

**연구2 UT**
- 기존안 vs 새로운 안(개선안) 비교
- 과업은 동일하게 유지
- 자동화 수준은 **높게 고정**
- 연구1의 시나리오를 동일하게 (오류 포함)
- 기존안과 개선안이 서로 너무 다르면 안 된다. 세련되고 예쁘게 만들지 않는다
- 연구2 결과를 설명할 때 가이드라인과 잘 연결해야 함 (어떤 가이드라인 때문에 이런 결과가 나왔는지 맵핑)

**가이드라인**
- 가이드라인이 얼마나 자세한지는 크게 중요하지 않음
- 가이드라인의 효과를 가장 잘 설명하는 방법: 완성된 가이드라인이 연구1 사용자평가에서 나온 내용(오류 등)을 다 설명할 수 있는지
  - 가이드라인이 어떤 항목에도 매칭되지 않으면 → 근거가 없는 것
  - 매칭되지 않는 발화·관찰이 남으면 → 필요한 가이드라인이 빠진 것
- 자동화 수준 관련 가이드라인(언제 통제권을 넘길지)도 포함하는 게 맞음 → 위계는 더 잘 맞도록 조정
- 분류는 2안(Cheng et al., 2026, CUA 디자인 스페이스)이 더 나음. 서브카테고리에 해당하는 것만 매칭하거나, 맞지 않으면 상위범주를 하나 더 제안. "참고해서 만들었고, 기반으로 했지만 우리 맥락에 맞춰 조정했다"고 명시

**시간이 되면**
- 전문가 평가: 가이드라인 항목이 MECE한지, 실제 발화·관찰과 연결되는지
- 다른 디자이너에게 가이드라인으로 디자인해 보게 하기

## 2. 용어 정의 (논문에서는 이 두 용어만 일관되게)

| 용어 | 정의 | 성격 |
|---|---|---|
| **오류** | 에이전트가 **사용자가 맡기지 않은 결정이나 정보 접근**을 하는 것 (위임 범위를 벗어난 행동). 선행연구에서 고령층의 통제감 상실과 관련된다고 보고된 행동을 바탕으로 정의 | 연구자가 설계로 정하는 것 (조작) |
| **통제감 상실** | 사용자의 반응 (반발, AI의 선택을 자기 실수로 여김, 경계, 개입 실패 등). 발화와 행동 관찰로 측정 | 측정하는 것 (결과) |

- 오류는 가설이다. 오류가 실제로 통제감 상실로 이어지는지는 측정해야 안다.
- 오류 3유형은 하나의 행동(맡기지 않은 결정·접근)을 세 측면에서 본 것이다.
  - **대리결정**: 누가 정했나 → AI가 사용자 대신 정함
  - **판단근거 미제공**: 왜 정했나 → 이유를 알리지 않음
  - **개인정보 접근 불투명**: 무엇을 봤나 → 어떤 정보를 무엇에 쓰는지 알리지 않음

### 오류와 자동화 수준은 다르다

- **자동화 수준**: 사용자가 **맡긴 일**을 진행할 때 단계마다 승인을 받느냐
- **오류**: 애초에 **맡기지 않은 일**을 AI가 하느냐

참가자는 "택시를 불러 달라"고만 했고, 요청사항 선택·이용내역 열람·예약은 맡긴 적이 없다.

| | 낮은 자동화 | 높은 자동화 |
|---|---|---|
| 맡긴 일 (출발지, 목적지 등) | 단계마다 승인 | 알리고 진행 |
| 맡기지 않은 일 (요청사항, 이용내역, 예약) | AI가 먼저 하고 나서 승인 요청 → **오류** | AI가 하고 진행 → **오류** |

→ 낮은 자동화에서 승인을 받아도 오류다(이미 고르고, 이미 본 뒤에 묻기 때문). 그래서 연구1에서 오류는 두 자동화 수준에서 똑같이 발생했다.

### 쓸 때 지킬 규칙

1. "오류"를 사용자 반응에 쓰지 않는다. ✗ "참가자가 오류를 겪었다" → ✓ "오류 상황에서 통제감 상실이 관찰되었다"
2. 오류를 "묻지 않음"이나 "통제감 상실 지점"으로 정의하지 않는다. "맡기지 않은 결정·접근"으로만 쓴다.
3. "개선안에서 오류가 발생하지 않았다"를 **결과**로 쓰지 않는다. 방법 부분에 "설계상 발생하지 않는다"로 쓰고, 결과에는 통제감 상실 비교만 쓴다.
4. 연구2에서는 오류 3유형을 따로 나누지 않고 "연구1과 같은 오류"로 묶어서 쓴다. 판단근거는 연구1 오류 정의에 이름만 나열하고 따로 논의하지 않는다(8번 Q&A 참고).

## 3. 연구 흐름

1. **선행연구**: 고령층의 통제감 상실과 관련된 에이전트 행동을 정리 → 오류 3유형 (가설)
2. **연구1**: 오류를 시나리오에 넣어 실제로 통제감 상실이 생기는지 관찰
   - 오류 상황에서 반발, AI의 선택을 자기 실수로 여김, 경계가 나타남
   - 오류가 아닌 곳에서도 통제감 상실이 나타남 (중지 버튼을 못 찾음, 실행화면 뜻 오해, 진행이 너무 빠름, 음성/보내기 버튼을 안 누름 등)
3. **가이드라인 도출**: 연구1에서 관찰된 통제감 상실 전체 → 요구사항 → 가이드라인 25개
4. **연구2**: 가이드라인을 적용하면 통제감 상실이 줄어드는지 검증

## 4. 오류 ↔ 연구1 장면 ↔ 가이드라인

| 오류 상황 (연구1 시나리오) | 오류 3유형 | 연구1에서 관찰된 반응 | 해당 가이드라인 |
|---|---|---|---|
| **세션1 · 기사님 요청사항**: AI가 이유 없이 ‘기사님과 이야기 나누며 가고 싶어요’를 고름 | 대리결정, 판단근거 미제공 | "나한테 왜 강요를 하지?"(P12), "추천보다 선택하는 게 좋지", "내가 뭘 잘못 눌렀나"(P13) | G20 선호가 필요한 결정은 먼저 묻기, G7 AI가 정한 것과 내가 한 것 구분 |
| **세션2 · 이용내역 + 예약**: 알리지 않고 최근 3개월 이용내역을 보고 다음 주 예약을 등록 | 개인정보 접근 불투명, 대리결정 | "내가 시킨 게 아닌데"(P04), "멋대로 잡는 건 절대 동의 안 한다"(P06), "내 일정을 오픈하고 싶지 않다"(P14) | G21 어떤 정보에 접근해 무엇에 쓰는지 공개, G22 접근 제한, G18 요청 외 행동은 실행 전 확인 |

- **G21.** AI는 어떤 정보에 접근해 무엇에 쓰는지 투명하게 공개해야 한다.
- **G22.** 시스템은 사용자가 AI의 정보 접근을 제한하거나 기록을 지울 수 있게 해야 한다.

※ 가이드라인 번호는 2안(CUA 디자인 스페이스 분류) 기준. 1안(시간순)에서는 "기록 삭제·접근 제한"이 25번.

## 5. 연구2 설계 (확정)

| 항목 | 내용 |
|---|---|
| 설계 | 참가자 내 설계. 한 참가자가 기존안과 개선안을 모두 체험 |
| 순서 | 참가자마다 기존안 먼저 / 개선안 먼저를 바꿈 (순서 효과 상쇄) |
| 체험 | 버전 2 × 세션 2 = 4회 |
| 과업·시나리오 | 연구1과 동일 (택시 호출, 과업 A/B) |
| 자동화 수준 | 높음으로 고정 |
| 오류 상황 | 세션1 기사님 요청사항, 세션2 이용내역 + 예약 (연구1과 동일, 새 오류 추가 없음) |
| 기존안 | 연구1 높은 자동화 프로토타입 그대로 → 오류 발생 |
| 개선안 | 가이드라인 1~25 적용 → 맡기지 않은 일은 하기 전에 사용자에게 넘김 → 오류 없음 |
| 화면 차이 | 색·레이아웃·앱 화면은 같고, 가이드라인이 요구하는 부분만 다름 |

### 오류 상황에서 두 안의 차이

| 오류 상황 | 기존안 (연구1 그대로) | 개선안 |
|---|---|---|
| 세션1 · 기사님 요청사항 | AI가 ‘기사님과 이야기 나누며 가고 싶어요’를 고르고 진행 | AI가 고르지 않고 목록(요청사항 없음 / 이야기 나누며 / 조용히)으로 먼저 물음 (G20). 최종 확인 전에 물어 최종 확인에 함께 보임 (G14) |
| 세션2 · 이용내역 + 예약 | 알리지 않고 이용내역을 보고 예약 등록 | 시작할 때 이용내역 접근을 끌 수 있음 (G22). 켜 두면 보기 전에 이유와 함께 [거부]/[허용]으로 물음 (G21). 예약도 [거부]/[예약하기]로 물음 (G18·G19) |

### 자동화 높음 고정과 G18의 적용 범위

피그마 「상세 구현」대로 출발지·목적지까지 모두 확인하면 개선안이 대부분 단계에서 먼저 물어 사실상 낮은 자동화처럼 동작한다. 그러면 "가이드라인 효과"와 "낮은 자동화로 바뀐 효과"가 섞인다. 그래서 G18("비가역적이거나 요청 외의 행동은 반드시 확인, 사소한 단계의 확인은 줄임")을 좁게 적용한다. 출발지·목적지는 맡긴 일이고, 되돌리기(G16)로 호출 전까지 되돌릴 수 있으므로 알리고 진행한다.

| 단계 | 맡긴 일? | 개선안 동작 | 근거 |
|---|---|---|---|
| 택시 앱 실행, 예상 금액 | 맡김 | 알리고 진행 | G18 사소한 단계 |
| 출발지, 목적지 | 맡김 | "~로 할게요" 먼저 알리고 8초 뒤 진행. 멈추기·되돌리기로 바꿀 수 있음 | G5·G11·G16 |
| 택시 종류 (과업 B) | 선호 필요 | 목록으로 물음 | G20 (요금이 달라짐) |
| 최종 호출 | 맡김, 비가역 | [수정]/[호출하기] | G14·G18 (결제) |
| 기사님 요청사항 (세션1) | **안 맡김** | 목록으로 물음 | G20 |
| 이용내역, 예약 (세션2) | **안 맡김** | [거부]/[허용], [거부]/[예약하기] | G18·G21 |

먼저 묻는 횟수 (과업 B): 기존안 0회 / 개선안 세션1 3회 · 세션2 4회 / (참고) 연구1 낮은 자동화 B1 승인 6회 + 오류 단계.
※ 프로토타입 설정에서 「넓게」(피그마대로 출발지·목적지도 확인)로도 바꿀 수 있음.

## 6. 측정

- **발화·관찰 코딩**: 연구1 FigJam의 통제감 상실 코드를 그대로 사용
  - 01 잘못된 수단을 믿음 → 작동하지 않음 (수단-결과, 전략신념)
  - 02 수단이 있어도 제때/제대로 쓸 수 있다는 믿음 부족 (행위자-수단, 능력신념)
  - 03 내 행동과 무관한 결과를 경험해 경계함 (행위자-결과, 통제신념)
  - 가능하면 기존안·개선안을 모르는 상태에서 코딩
- **행동 지표** (프로토타입 로그, 두 버전 공통)
  - 최종 결과가 참가자 의도대로 됐는지 (요청사항, 예약 여부 등)
  - 개입 방식과 성공 여부, 오류 노출 → 반응까지 시간
  - 실행화면을 누른 횟수, 휴대폰 뒤로 가기 횟수, 중지·직접 조작 횟수
- **가이드라인 맵핑**: 개선안 로그에 가이드라인이 작동한 순간을 번호로 기록 (`g` 열, 요약 `guideline_use`)
- **범위**: 오류 상황만이 아니라 과업 전체 (오류가 아닌 곳의 통제감 상실도 비교)
- **해석 기준 (교수님 코멘트)**: 연구1 발화·관찰이 개선안에서 사라지면 해당 가이드라인의 효과, 남아 있으면 필요한 가이드라인이 빠진 것

## 7. 논문 문장 예시

### 7-1. 용어와 오류 정의 (방법 첫머리)
> 본 연구에서 **오류**는 에이전트가 사용자가 맡기지 않은 결정이나 정보 접근을 하는 것으로 정의하였다. 선행연구에서 고령층의 통제감 상실과 관련된다고 보고된 에이전트 행동을 바탕으로, 오류를 대리결정, 판단근거 미제공, 개인정보 접근 불투명의 세 유형으로 구성하였다. **통제감 상실**은 사용자의 반응으로, 발화와 행동 관찰을 통해 측정하였다. 오류는 연구자가 설계로 조작한 변수이며, 오류가 실제로 통제감 상실로 이어지는지는 측정을 통해 확인하였다.

### 7-2. 오류와 자동화 수준의 관계
> 오류는 자동화 수준과 독립적이다. 자동화 수준은 사용자가 맡긴 과업을 진행할 때 단계마다 승인을 받는지를 의미하며, 오류는 사용자가 맡기지 않은 결정이나 정보 접근을 하는지를 의미한다. 연구1의 낮은 자동화에서도 에이전트는 사용자가 맡기지 않은 선택과 열람을 먼저 수행한 뒤 승인을 요청하였으므로, 오류는 두 자동화 수준에서 동일하게 발생하였다.

### 7-3. 연구1 방법
> 택시 호출 과업 시나리오에 오류 상황 2곳(기사님 요청사항, 이용내역 기반 예약)을 포함하였다. 자동화 수준은 높음과 낮음 두 가지로 구성하였다. 낮은 자동화에서는 에이전트가 단계마다 사용자의 승인을 요청하였고, 높은 자동화에서는 승인 없이 진행하였다. [참가자 배정 방식: 실제 진행대로 기입 — 예: 각 참가자가 두 자동화 수준을 모두 경험했는지, 세션1·2와 자동화 수준의 짝, 순서 역균형화 방법]

### 7-4. 연구2 방법
> 연구2는 연구1과 같은 시나리오를 사용하고, 자동화 수준은 높음으로 고정하였다. 참가자는 기존안과 개선안을 모두 체험하였으며(참가자 내 설계), 체험 순서는 참가자마다 바꾸어 순서 효과를 상쇄하였다. 기존안은 연구1의 프로토타입으로, 연구1과 같은 오류가 발생한다. 개선안은 도출한 가이드라인을 적용한 프로토타입으로, 같은 상황에서 에이전트가 사용자가 맡기지 않은 결정과 정보 접근을 수행하기 전에 사용자에게 먼저 묻는다(G18, G20, G21, G22). 따라서 개선안에서는 설계상 연구1의 오류가 발생하지 않는다. 두 안에서 참가자의 통제감 상실을 비교하였다.

### 7-5. 자동화 수준 고정과 G18 적용 범위
> 개선안은 높은 자동화를 기본으로 하되, 가이드라인 18에 따라 비가역적인 결정(최종 호출), 사용자의 선호가 필요한 결정(택시 종류, 기사님 요청사항), 사용자가 요청하지 않은 행동(이용내역 열람, 예약)에서만 사용자에게 먼저 확인을 요청하였다. 출발지와 목적지는 사용자가 맡긴 과업이고 되돌리기 기능(G16)을 통해 호출 전까지 되돌릴 수 있으므로, 에이전트가 먼저 알린 뒤 진행하도록 하였다(G5, G11).

### 7-6. 가이드라인 분류 출처 (교수님 코멘트)
> 가이드라인은 Cheng et al.(2026)의 컴퓨터 사용 에이전트 UX 디자인 스페이스 분류를 참고하여 정리하였다. 해당 분류를 기반으로 하되, 본 연구의 구체적인 맥락(고령 사용자의 모바일 앱 대리조작)에 맞추어 하위범주를 조정하였다.

### 7-7. 한계 (선택)
> 개선안은 가이드라인에 따라 일부 상황에서 먼저 확인을 요청하므로, 기존안보다 확인 횟수가 많다(과업 B 기준 세션1 3회, 세션2 4회). 따라서 두 안의 차이에는 표현 방식뿐 아니라 통제권을 넘기는 시점의 차이가 함께 포함된다. 또한 개선안에서 참가자가 이용내역 접근을 처음부터 허용하지 않으면 세션2의 오류 상황에 노출되지 않는다.

## 8. 심사 대비 Q&A (본문에는 쓰지 않고, 질문을 받으면 답할 근거)

**Q1. 오류를 없앤 개선안에서 통제감 상실이 줄어든다는 건 당연한 것 아닌가? (순환논리)**
→ 오류는 에이전트의 행동(조작)이고, 통제감 상실은 사용자의 반응(측정)으로 따로 정의했다. 개선안에 오류가 없는 것은 설계 차이일 뿐이고, 통제감 상실이 줄어드는지는 어느 쪽으로도 나올 수 있다. 예를 들어 AI가 먼저 물어도 부담을 느끼거나(연구1 P13: 단계마다 확인하면 힘들다) 질문의 뜻을 몰라 아무거나 고를 수 있다. 연구1에서도 오류가 아닌 곳에서 통제감 상실이 나타났고, 이는 오류와 통제감 상실이 별개의 개념이라는 근거다.

**Q2. 왜 개선안에는 연구1의 오류를 넣지 않았나?**
→ 연구1의 오류는 "맡기지 않은 결정·접근"으로 정의되어 있고, 가이드라인(G18, G20, G21)은 바로 이것을 하기 전에 사용자에게 넘기라고 한다. 따라서 가이드라인을 적용한 개선안에는 정의상 이 오류가 존재할 수 없다. 두 안에 같게 둔 것은 오류가 나던 상황(시나리오)이며, 그 상황을 기존안은 오류로, 개선안은 가이드라인대로 처리한다. 연구1에 없던 새 오류는 시나리오 동일성을 위해 추가하지 않았다.

**Q3. 오류의 "맡기지 않은"이 결국 자동화 수준과 같은 것 아닌가?**
→ 다르다. 자동화 수준은 맡긴 일을 진행할 때 단계마다 승인을 받는지이고, 오류는 맡기지 않은 일을 하는지다. 연구1 낮은 자동화에서도 AI는 맡기지 않은 선택·열람을 먼저 수행한 뒤 승인을 요청했으므로 오류가 똑같이 발생했다(2번 표).

**Q4. 판단근거 미제공은 연구2에서 어떻게 되나?**
→ 판단근거 미제공은 세션1에서 대리결정과 같은 상황에서 함께 발생한다. 개선안은 AI가 고르지 않으므로 근거를 댈 대상이 없어 함께 사라진다. 따라서 연구2 결과는 두 유형을 묶은 오류에 대한 것이며 판단근거만의 효과는 주장하지 않는다. 연구1에서 참가자들은 오히려 근거 제공을 부담스러워했고(P13: "이유까지 있는 건 너무 과하다", P14: "왜 추천했는지는 별로 궁금하지 않다"), 통제감 상실은 근거의 부재보다 AI가 대신 골랐다는 것(P12, P13)과 누가 정했는지 모른다는 것(P13: "내가 뭘 잘못 눌렀나")에서 나타났다. 그래서 판단근거 전용 가이드라인은 두지 않고, 부가 정보 일반 원칙(G10: 핵심만 보여주고 부가 정보는 원할 때)의 한 사례로 포함했다. G10은 「볼 게 너무 많아 혼란스러움」(P07, P12, P00)에서도 함께 도출된 일반 원칙이다.

**Q5. 개선안은 질문이 많아 낮은 자동화와 비슷한 것 아닌가?**
→ 맡긴 일(앱 실행, 출발지, 목적지, 예상 금액)은 기존안처럼 알리고 진행한다. 먼저 묻는 것은 비가역적 결정(최종 호출), 선호가 필요한 결정(택시 종류, 요청사항), 맡기지 않은 일(이용내역, 예약)뿐이다(5번 표). 연구1 낮은 자동화보다 확인 횟수가 적다.
